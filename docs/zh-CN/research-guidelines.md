# 研究规范

OpenMicroDuck 只发布适合公开研究仓库披露的资料。

## 证据标签

- **官方产品规格**：官方产品页 / Press Kit 发布的规格；
- **官方源码**：可直接从官方代码、配置、文档或仿真资产验证；
- **Measured / 实测**：有方法和条件记录的物理测量；
- **Observed / 观察**：黑盒、拆解、协议或行为直接观察；
- **Inferred / 社区重建**：根据公开证据推导，但没有获得官方直接确认；
- **Assumed / 假设**：研究或仿真的临时假设；
- **Provisional / 暂定**：官方开发资料中存在，但明确尚未最终冻结。

## 仅公开资料原则

不得提交：

- 保密、泄露、私有或未公开项目资料；
- 账号、凭据、设备 secret、private key 或个人信息；
- 未经授权获得的专有 CAD、PCB、原理图、固件或内部文档；
- 仅因为“可供比较”就加入的无关私有工程资料；
- 没有兼容权利和 attribution 的第三方资产。

## 文档必须让普通读者先看懂

技术准确还不够。普通说明文档必须先让不了解机器人、Linux、强化学习的人知道“它在干什么”。

统一采用这些写法：

1. **先说功能，再说代码名。** 写“摄像头和视频服务（`mediad`）”，不要一上来只写 `mediad`。
2. **先画整体流程，再列模块。** 能用一张小图说明的，不要先堆十几个目录名和协议名。
3. **术语第一次出现时，用一句普通话解释。** 例如 daemon、observation、policy、IPC、kinematics。
4. **不要连续堆名词。** 一句话里不要要求读者同时理解多个框架、协议和源码目录。
5. **概览和参数表分开。** 参数页可以很详细，但前面必须先有“这些参数是干什么的”。
6. **不要重复解释同一件事。** 一张图能说清楚，就不要再写三段近似描述。
7. **段落尽量短。** 一段只讲一个问题。
8. **前面先回答四个问题：** 这是什么？负责什么？在整机哪个位置？哪些已确认、哪些还未知？

软件架构优先使用这种顺序：

```text
传感器
  ↓
感知
  ↓
高层行为判断
  ↓
运动 Policy
  ↓
电机控制
```

读者先理解这条线以后，再介绍 `tofd`、`mediad`、`robotd`、JSON-RPC、Unix socket、RKNN、ONNX Runtime 等实现名称。

## 逆向研究文档应说明

1. 使用了什么公开资产或实物观察；
2. 结论如何推导；
3. 仍有哪些不确定性；
4. 描述的是仿真模型、开发机还是量产产品；
5. 对应 revision / commit / firmware version。

优先自行绘制示意图和表格，不直接搬运第三方图形资产。

## 可复现性

测量资料在适用时应记录：硬件 revision、软件/固件版本、source commit、仪器、测试条件、单位、sample count、不确定度/变化范围和原始数据位置。

## 来源冲突

不能为了文档整洁把冲突删除。公开来源不一致时，应记录冲突，并说明每个结论采用哪个来源及理由。

## 翻译规则

英文与简体中文应保持同一技术含义。翻译版不得把原文的“推测/暂定”强化成“已确认”。未来增加其它语言时同样适用。
